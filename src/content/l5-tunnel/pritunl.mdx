## 什么时候需要一套"VPN 系统"

前两节的 WireGuard 和 Tailscale 解决的是**连通性**。但企业场景里还有一类需求，
它们和连通性无关：

| 需求 | WireGuard 裸配 | Tailscale | Pritunl |
| --- | --- | --- | --- |
| 谁能连、谁不能连 | 手工发密钥 | ACL + IdP | **组织与用户模型** |
| 离职回收 | 手工删 peer | IdP 联动 | **后台点一下 / SSO 联动** |
| 谁在什么时候连过 | 无 | 有日志 | **审计事件可导 SIEM** |
| 强制 MFA | 无 | 靠 IdP | **内置 TOTP / 推送 / 设备认证** |
| 给不懂技术的人发配置 | 手工 | 装客户端登录 | **邮件发 profile** |
| 兼容既有 OpenVPN 客户端 | 不兼容 | 不兼容 | **兼容** |

**一句话判断**：如果问题是"几台服务器互联"，用 WireGuard；
如果问题是"几十上百个人要按权限接入内网、还要能审计"，那才需要 Pritunl 这类系统。

## 架构：MongoDB 是协调层

Pritunl 的架构有一个和其它方案很不一样的设计：**所有节点间通信都通过 MongoDB**。

```
        ┌──────────── MongoDB（协调层）────────────┐
        │   配置、用户、证书、节点状态、路由         │
        └───┬──────────────┬──────────────┬────────┘
            │              │              │
      ┌─────▼────┐   ┌─────▼────┐   ┌─────▼────┐
      │ pritunl-1│   │ pritunl-2│   │ pritunl-3│   ← 节点之间不直接通信
      │ (Web+VPN)│   │          │   │          │
      └──────────┘   └──────────┘   └──────────┘
```

带来的两个特性：

- **节点之间不需要开防火墙互通**——它们只和 MongoDB 说话
- **所有节点地位相等**，任何一个挂了其它的照常独立工作

代价也很明确：**MongoDB 成了那个必须自己保证高可用的组件**。
它挂了，管理面和新连接就出问题。

<Callout type="warn" title="MongoDB 是这套方案里真正的单点">
很多人部署时按文档装个单机 MongoDB 就上线了，然后把精力全花在 VPN 节点的冗余上——
方向反了。

要做的事：
- MongoDB 用**副本集**（至少 3 节点），不要单机
- **备份策略**要覆盖它：证书、用户、组织全在里面，丢了等于全部重来
- 监控它的可用性与磁盘

VPN 节点反而好办：多装几台指向同一个 MongoDB 就是集群。
</Callout>

## 三种协议，各管一段

| 协议 | 用途 | 特点 |
| --- | --- | --- |
| **OpenVPN** | 客户端接入 | 兼容所有 OpenVPN 客户端，包括 Chromebook 等受限平台 |
| **WireGuard** | 客户端接入 + **高性能站点互联** | 性能好，现代客户端首选 |
| **IPsec** | 站点互联、VPC 对等 | 与传统网络设备、云厂商 VPN 网关对接 |

选择逻辑：**人接入用 WireGuard（性能）或 OpenVPN（兼容性）；
网对网用 IPsec（对端多半是传统设备或云网关）。**

## 核心对象模型

Pritunl 的配置是三层结构，理解它就会配了：

```
组织（Organization）           ← 一组用户，比如「研发部」「外包」
  └─ 用户（User）              ← 一个人一个，生成独立证书
服务器（Server）               ← 一个 VPN 实例：监听端口、地址池、路由
  └─ 挂载组织                  ← 决定哪些人能连这个服务器
```

关键点是**服务器和组织是多对多的**：

- 一台"生产内网"服务器可以只挂「运维组织」
- 一台"测试环境"服务器同时挂「研发」和「外包」两个组织
- 换句话说：**权限边界靠"哪个组织挂在哪台服务器上"来划**

### 路由：决定客户端能访问什么

服务器对象上配置要下发给客户端的路由：

```
10.0.0.0/8       → 内网全放通
10.0.99.0/24     → 带外网（通常不放）
0.0.0.0/0        → 全流量走 VPN（出口模式）
```

<Callout type="tip" title="别默认下发 0.0.0.0/0">
下发默认路由意味着**客户端的全部流量都走 VPN**。后果：

- 你的出口带宽要承载所有人的日常上网
- 用户体验变差（延迟增加）
- 出口 IP 被滥用的风险落到你头上

**只下发真正需要的内网段**（分流模式）是绝大多数场景的正解。
只有明确要"统一出口审计"时才下发默认路由——而那是另一个需求，
要单独评估带宽与合规。

这和 [Mihomo 分流规则](/learn/l5-tunnel/clash-rules) 里"该直连的直连"是同一个道理。
</Callout>

## 身份与认证：这才是它的核心价值

```
SSO：       SAML / Google Workspace / Okta / OneLogin / Microsoft Entra
            / Auth0 / JumpCloud / Duo / Radius
MFA：       TOTP、推送通知、设备认证（TPM / Apple Secure Enclave）
DNS 映射：  user0.org0.vpn 这种可读名字
```

接上 SSO 之后，**账号生命周期就交给了 IdP**：

| 事件 | 效果 |
| --- | --- |
| 新员工入职 | IdP 里加人 → 自动能连 |
| 转岗 | 改 IdP 组 → 权限跟着变 |
| **离职** | **IdP 停用 → VPN 立刻连不上** |

这是它相对"手工发 WireGuard 配置"最大的差别：
**手工发的密钥，人走了你得记得删；接了 SSO，停用账号就自动失效。**

## 站点互联与高可用

除了人接入，Pritunl 也做网对网：

| 能力 | 说明 |
| --- | --- |
| **Gateway Link** | 站点到站点连接，支持失效切换 |
| **拓扑** | hub-and-spoke 与 mesh 都支持 |
| **Pritunl Link** | 专用的站点互联客户端，**不需要连数据库** |
| **多云 VPC 对等** | AWS / GCP / Azure / Oracle / Hetzner |
| **AWS 路由表联动** | 动态改 VPC 路由表 |
| **HA** | 服务器复制 + 自动故障切换；跨可用区用 VXLAN |

站点互联这块和 [Tailscale 的 subnet router](/learn/l5-tunnel/tailscale) 是竞争关系，
区别在于：Pritunl 更贴近传统网络的做法（IPsec、路由表、网关），
Tailscale 更贴近"每台机器都装客户端"的思路。

## 开源版与付费档的边界

这是选型时必须先看清的一条，因为**很多人以为免费版就够，上线才发现关键功能在付费档**：

| 档次 | 关键能力 |
| --- | --- |
| **Community（免费）** | **一台服务器**，用户与设备数不限 |
| **Premium** | 端口转发、gateway link 与失效切换、配置同步、邮件发密钥 |
| **Enterprise** | **SSO、TPM/Secure Enclave 认证、自动故障切换、复制、VXLAN、
AWS VPC 集成、站点互联与 IPsec、多云对等、DNS 映射、监控、高级审计、多管理员、插件、API** |

按服务器数收费，每台服务器上的 VPN 实例、用户与连接数不限。

<Callout type="warn" title="SSO 在 Enterprise 档">
这一条最容易踩：**SSO、审计、复制、API 都在 Enterprise**。
而"接 SSO 做账号生命周期管理"往往正是选 Pritunl 的初衷——
如果预算只批了免费版，那它相对 WireGuard 的核心优势基本不存在。

选型时先把"必须有的功能"列出来对照档次，别等 POC 完了才发现。
</Callout>

## 部署与运维要点

```bash
# 装（以 RHEL 系为例，Debian/Ubuntu 类似）
# 加 Pritunl 与 MongoDB 仓库后：
dnf install -y pritunl mongodb-org
systemctl enable --now mongod pritunl

# 首次进 Web 界面需要的 setup key
pritunl setup-key
# 默认管理员密码
pritunl default-password
```

运维上值得注意的几点：

```bash
# 服务状态与日志
systemctl status pritunl mongod
journalctl -u pritunl -f

# 主机侧必须开转发（和 WireGuard 那节一样）
sysctl net.ipv4.ip_forward

# 看当前连接
# Web 界面 → Users 页有在线状态；API 也能拉
```

<Callout type="trap" title="它会动主机防火墙">
Pritunl 有"动态防火墙"设计，会自己往 iptables 里加规则。这意味着：

- 你的主机加固脚本和它可能**互相覆盖**——和 [Pod 不通那一关](/learn/l1-k8s/quest-pod-unreachable)
  里安全加固规则拦掉 VXLAN 是同一类问题
- 排查"连上了但访问不了内网"时，要同时看 **Pritunl 的路由配置** 和 **主机 iptables/nftables**
- SELinux 策略同理

改主机防火墙前先确认它对 VPN 端口与转发规则的影响。
</Callout>

## 三种方案怎么选

| 你的问题 | 选 |
| --- | --- |
| 几台服务器要互联，成员基本不变 | **裸 WireGuard** |
| 设备到处跑、都在 NAT 后、成员常变 | **Tailscale** |
| 不接受控制面在第三方 | **Headscale** 自建 |
| **几十上百人按权限接入，要 SSO 与审计** | **Pritunl** |
| 要兼容既有 OpenVPN 客户端 / 受限平台 | **Pritunl** |
| 要和传统网络设备、云网关做 IPsec 对接 | **Pritunl** |

再强调一次判断标准：**这是"连通性问题"还是"身份与合规问题"？**
前者用轻量方案，后者才值得引入一套系统。

## 这节课的落点

- 判断标准：**这是连通性问题还是身份与合规问题**——后者才值得上一套系统
- 架构上 **MongoDB 是协调层**：节点间零防火墙需求、所有节点对等，
  但**它才是真正的单点**，要副本集 + 备份
- 三种协议分工：人接入用 WireGuard（性能）或 OpenVPN（兼容），网对网用 IPsec
- 对象模型：**组织 × 服务器的挂载关系就是权限边界**
- 路由**只下发必要内网段**，别默认给 `0.0.0.0/0`
- 核心价值是**账号生命周期交给 IdP**：离职停用即失效，不用记得删密钥
- **SSO、审计、复制、站点互联都在 Enterprise 档**，选型前先对照功能与档次
- 它会动主机防火墙，与主机加固脚本可能互相覆盖，排障要两边一起看
