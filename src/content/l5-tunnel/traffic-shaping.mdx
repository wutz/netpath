## 问题不是加密强度

现代代理协议用的都是成熟密码学，**内容本身没人解得开**。协议还在不停演进，
是因为要解决另一个问题：

> 加密流量看起来"像什么"。

这一节讲可观测特征有哪些、协议怎么减少它们、以及每种手段的代价。
它是理解"为什么协议一直在换"的技术底层。

## 可观测特征清单

即使内容不可解密，中间设备仍然能看到这些：

| 特征 | 具体内容 |
| --- | --- |
| **握手指纹** | TLS ClientHello 里的密码套件顺序、扩展列表、ALPN、GREASE 值 |
| **证书与 SNI** | 目标域名（SNI 明文）、证书链、有效期 |
| **包长分布** | 每个包多大、大小的分布形状 |
| **时序** | 请求间隔、突发模式、连接持续时间 |
| **连接模式** | 一个 IP 上有多少并发连接、连接建立频率 |
| **端口与协议** | 目的端口、传输层类型 |
| **主动探测响应** | 别人直接连你这个端口时，你返回什么 |

**内容加密只挡住了"读得懂"，挡不住"看得出"。**

## TLS in TLS：嵌套握手的固有问题

这是当前最核心的一个技术问题。代理把 TLS 流量装进自己的 TLS 连接时：

```
外层 TLS 握手（代理与服务器）
   └─ 建立完成后，里面开始跑：
      内层 TLS 握手（浏览器与目标网站）
         ↑ 这个握手的包长与时序模式，在外层加密后依然有迹可循
```

问题在于**握手是有固定形状的**：ClientHello 一般偏小、ServerHello 加证书偏大、
后续几个包大小相对固定、时序也有规律。这些特征即使被外层加密包住，
**包长序列和时间间隔仍然暴露在外**。

于是可以判断：这条"普通 HTTPS 连接"建立后不久，里面又发生了一次 TLS 握手——
而正常的 HTTPS 浏览不会这样。

## 缓解思路：改变形状

[anytls](https://github.com/anytls/anytls-go) 这类协议正是**为缓解 TLS in TLS 指纹而设计**的。
它的三个手段：

| 手段 | 做什么 | 减少了哪个特征 |
| --- | --- | --- |
| **灵活的分包策略** | 不按原始边界切，重新划分数据块 | **包长分布** |
| **填充策略** | 往包里塞无意义字节，改变长度 | **包长分布** |
| **连接复用** | 多个请求走同一条已建立的连接 | **握手频次**——少产生嵌套握手 |

第三点值得单独说：**减少嵌套握手的最好办法是不要反复建立它**。
连接复用既降低了延迟（省掉握手往返），也顺带减少了可观测的握手次数——
一举两得，这也是它被列为核心特性的原因。

<Callout type="warn" title="参考实现不等于生产客户端">
anytls-go 的项目定位写得很明确：它是**协议的参考实现**，
目的是展示协议细节、交互流程与边界场景，**不是给日常使用的客户端**。

而且它的示例服务端与客户端**默认采用不安全的配置**——
假定你不会遇到 TLS 中间人攻击。这个假定不成立时，流量可能被拦截。

日常使用应该用实现了该协议的成熟软件（sing-box、mihomo 等），
并且**自己确认 TLS 校验相关的配置是打开的**。

顺带一提：各家第三方实现与规范的贴合程度由各自团队负责，
不同版本行为可能有差异——这也是"换客户端后行为变了"的常见原因。
</Callout>

```bash
# 参考实现的用法（仅用于理解协议，不建议直接生产使用）
./anytls-server -l 0.0.0.0:8443 -p <密码>
./anytls-client -l 127.0.0.1:1080 -s <服务器>:8443 -p <密码>
# 新版本支持 URI 形式
./anytls-client -l 127.0.0.1:1080 -s "anytls://<密码>@<服务器>:<端口>"
```

## 主动探测与 probe_resist

被动观察之外还有**主动探测**：直接连你那个端口，看它怎么回应。

```
正常的 HTTPS 服务：返回网页，证书匹配域名
配置粗糙的代理：  返回错误、直接断开、或返回可识别的特征响应
                  ← 这本身就是特征
```

[gost](/learn/l5-tunnel/gost-toolbox) 那节提到的 `probe_resist` 就是应对这个：
**没有正确凭据的访问，返回一个正常网页**。

```bash
gost -L "http2://user:pass@:443?cert=/path/fullchain.pem&key=/path/privkey.pem\
&probe_resist=file:/var/www/index.html"
```

配套要做的三件事：

1. **真实域名 + 真实证书**（Let's Encrypt 即可）——自签证书本身就是强特征
2. **端口用 443**——非标准端口上跑 TLS 是另一个特征
3. **伪装页面要像样**——返回默认 nginx 欢迎页比返回空白更自然

## CDN 前置

当出口 IP 本身成为问题时（被封或被限速），可以把 CDN 挡在前面：

```
客户端 → CDN 边缘节点（大量正常流量共用的 IP）→ 回源到你的服务器
```

两个硬性约束来自 CDN 的工作方式：

| 约束 | 原因 |
| --- | --- |
| **必须用 WebSocket 类传输**（`wss` / `mwss`） | CDN 只代理 HTTP 语义的流量，裸 TCP 隧道过不去 |
| **端口限于 80/8080/443/8443 等** | CDN 只在标准 HTTP(S) 端口上接受回源配置 |

```bash
# 服务端：WebSocket over TLS，带多路复用
gost -L "relay+mwss://user:pass@:443?cert=...&key=..."
# 客户端：连 CDN 域名
gost -L :1080 -F "relay+mwss://user:pass@cdn-domain.example.com:443"
```

代价也很实在：

- **多一跳，延迟增加**
- CDN 的连接数与流量可能产生费用
- **回源 IP 仍可能被识别**，CDN 只是遮住了直连关系

<Callout type="tip" title="mwss 里的 m 是多路复用，在 CDN 场景收益特别大">
`wss` 是 WebSocket over TLS，`mwss` 多了多路复用。经 CDN 时每建一条新连接都要
完整走一遍 TLS 握手 + CDN 的回源建连，开销明显。

多路复用把多个逻辑连接塞进一条物理连接，**既降延迟又减少握手次数**——
和 anytls 的连接复用是同一个思路。
</Callout>

## 另一类问题：原生 IP

有些服务不是"能不能连上"的问题，而是**连上了但被目标站点风控**：
数据中心 IP 会被识别并限制（流媒体、部分 AI 服务、部分电商）。

这与前面讲的特征无关，属于**IP 归属**问题。常见处理是用 WARP 这类服务拿一个
"住宅属性"更强的出口：

```bash
# 代理模式：本地起一个 SOCKS5，只把需要的流量送过去
warp-cli registration new
warp-cli mode proxy
warp-cli connect
# 默认监听 127.0.0.1:40000
```

然后在 gost 或 Mihomo 里**只把特定域名分流到它**，其余照常走自己的出口。

```bash
gost -L :1080 -F "socks5://127.0.0.1:40000?bypass=~*.需要原生IP的域名"
```

<Callout type="warn" title="WARP 的两个运维注意点">
- **内存泄漏**：长期运行的实例存在内存缓慢增长的情况，实践中通常配一个定期重启
- **文件描述符**：并发高时要调大 `LimitNOFILE`，否则会出现连接失败

它更适合作为**特定域名的旁路出口**，而不是承载全部流量的主链路。
</Callout>

## 代价对照表

每种手段都不是免费的：

| 手段 | 收益 | 代价 |
| --- | --- | --- |
| 灵活分包 + 填充 | 改变包长分布 | **有效载荷率下降**（填充占带宽） |
| 连接复用 | 减少握手、降延迟 | 单连接故障影响面变大（队头阻塞） |
| 真实证书 + probe_resist | 抗主动探测 | 要维护域名与证书续期 |
| CDN 前置 | 遮住直连关系 | **多一跳延迟** + 费用 + 只能用 WS 类传输 |
| WARP 旁路 | 解决 IP 归属 | 多一跳 + 需要运维（重启、fd 上限） |

**一个务实的原则：从最简单的开始，遇到具体问题再加一层。**
一上来就把所有手段叠满，结果是延迟高、配置复杂、出问题难定位——
而多数场景根本用不到那么多。

## 这节课的落点

- 协议演进不是因为加密不够强，是因为**加密流量"看起来像什么"**
- 可观测特征：握手指纹、SNI 与证书、**包长分布、时序**、连接模式、主动探测响应
- **TLS in TLS** 的问题是内层握手的包长与时序在外层加密后仍可识别
- 三个缓解手段：**灵活分包、填充、连接复用**；其中连接复用一举两得（降延迟 + 少握手）
- 参考实现 ≠ 生产客户端；**示例配置默认不校验中间人**，生产要用成熟软件并确认 TLS 校验
- 抗主动探测靠 `probe_resist` + **真实域名与证书 + 标准端口**，三者缺一不可
- CDN 前置有两个硬约束：**必须 WebSocket 类传输、端口限标准 HTTP(S) 端口**
- "原生 IP"是另一类问题（IP 归属而非流量特征），用 WARP 做**特定域名的旁路出口**
- **从最简单的开始，遇到问题再加一层**，叠满手段只会让延迟与排障成本一起上升
